Продолжение `verdict-2.md` после находок `verdict-3.md` о контракте харнесса.
Метод тот же: реплей реальных траекторий контекста всех 1339 workflow-агентов
(`e_cap.py`, `e2_hard.py`, `e2_soft.py`, `e2_comply.py`). Калибровка не менялась:
допущение C (CAP=30, E=2, H=6k) воспроизводится как +17.9 % против 18.6 % у C и 18.17 % у B.

Принимаю три находки verdict-3 без возражений: у `agent()` нет `maxTurns`; потолок живёт
только во фронтматтере `.claude/agents/*.md` (то есть **B-M1 — жёсткая предпосылка**);
при упоре харнесс делает `break` без финального хода.

## Жёсткий break (кривая, число)

### Какой из моих классов соответствует «оборванному без прощального слова»

В `verdict-2.md` я мерил E двумя способами: **брутто** `W₂` (все ходы до первого
содержательного действия) и **нетто** `A+B` (за вычетом новой земли, которую
неразрезанный агент прошёл бы всё равно). Разделение имело смысл ровно потому, что
handoff-файл говорит продолжению, какая земля уже пройдена.

**При жёстком break'е этого файла нет, и разделение схлопывается:** продолжение не может
отличить «уже исследовано» от «нового» и перепроходит разведку целиком. Значит цена шва —
**брутто-мера**, а не нетто:

| популяция | брутто `W₂`, ходы | что у продолжения было на входе |
|---|---:|---|
| RETRY-имплементер | **9.0** | бриф + boundary + работа на диске + структурированный список нарушений |
| fix-агент | **12.0** | бриф + findings с файлом и строкой |
| объединённо (n=38) | **11.5** | — |
| холодный имплементер (контроль) | **13.0** | только бриф — ровно положение оборванного сегмента |

**E_hard = 11.5 хода (полоса 9–13), ≈ 285–410 k токенов на шов.**
**Для этого варианта число D (13 ходов / 397 k) подтверждаю — оно измеряет именно его.**
Мои E=7/220 k относятся к варианту с написанным handoff-файлом, которого здесь нет.

Проверил и отдельное допущение «на диске лежит недописанный отчёт, он сработает как handoff» —
**неверно**. Ролевые агенты пишут `.mvp/reports/task-NNN.md` **один раз** (медиана 1 запись,
p75 = 1) и **на 97 % своей жизни** (медиана — ход 34 из ~37):

| | агентов длиннее CAP | из них отчёт уже написан к ходу CAP |
|---|---:|---:|
| CAP=25 | 127 | 5 = **4 %** |
| CAP=30 | 107 | 4 = **4 %** |
| CAP=40 | 73 | 4 = **5 %** |

В 96 % случаев обрыв застаёт пустой отчёт. Поэтому в кривой ниже `H = 0`, а не 2–6 k.

### Почему «+9 % убытка» — это не E=13, а двойной счёт

verdict-3 начисляет одновременно **E=13 ходов разогрева И `H = 60 k`** постоянного контекста,
трактуя 397 k D как размер handoff-материала. Это одна и та же величина, начисленная дважды.
Прямая арифметика моего реплея: при E=13 сумма контекстов самих разогревочных ходов равна

```
Σ (base + j·2200), j = 0..12,  base = ctx₀ + H = 20 k   →   431 600 токенов
```

то есть **измеренные D ≈397 k уже полностью оплачены ходами разогрева**. `H` — это размер
файла, который продолжение читает (5–6 k), а не стоимость шва.

Реплей обоих вариантов на одних траекториях:

| вариант | прогон `wf_4d14cdc2` | корпус 867 М |
|---|---:|---:|
| CAP=30, E=13, **H=60 k** (счёт verdict-3) | **−18.7 % (убыток)** | −16.5 % (убыток) |
| CAP=40, E=13, H=60 k | −7.5 % (убыток) | −3.9 % (убыток) |
| CAP=30, E=13, H=6 k | **+6.1 %** | +13.6 % |
| CAP=30, E=13, H=0 | **+7.9 %** | +15.8 % |

Знак механизма переворачивает не измеренное E, а **приписанный `H = 60 k`**.
Число «+9.0 % убытка» из verdict-3 воспроизводится (у меня −18.7 %, тот же знак и порядок)
ровно и только при двойном начислении.

### Кривая жёсткого break'а (H = 0, E по брутто-мере)

Ячейка: **% прогона `wf_4d14cdc2` / % workflow-корпуса**.

| CAP | E=9 (низ полосы) | **E=11.5 (центр)** | E=13 (верх полосы, число D) |
|---:|---:|---:|---:|
| 20 | +12.7 % / +24.6 % | +4.0 % / +15.0 % | −5.4 % / +6.0 % |
| **25** | +13.6 % / +24.3 % | **+10.2 % / +20.2 %** | +5.3 % / +14.8 % |
| **30** | +12.7 % / +21.9 % | **+10.7 % / +19.5 %** | +7.9 % / +15.8 % |
| 40 | +9.4 % / +16.5 % | +8.4 % / +15.3 % | +7.0 % / +13.4 % |
| 50 | +6.0 % / +11.0 % | +5.0 % / +10.4 % | +4.4 % / +9.2 % |

**Жёсткий break при измеренной цене возобновления положителен на всей полосе E при CAP ≥ 25.**
Отрицательным он становится только при CAP=20 и E≥13 — и это ровно тот угол, куда попал D
со своей степенной моделью. Оптимум — **CAP = 25–30**, число **+10.5 % прогона / +19.5 %
корпуса** по центру полосы, вилка **+7.9…+13.6 % / +14.8…+24.3 %**.

### Цена пустого финала (park ~371 k)

Обрыв без `STATUS:` → `parseStatus` отдаёт `BLOCKED` → park. Реализуемый суррогат
verdict-3 (ветка «ответ без `STATUS:` ⇒ диспатч продолжения») это снимает; вопрос — цена
промахов. `q` — доля швов, всё-таки обернувшихся park'ом:

| CAP / E | швов (прогон / корпус) | q\* при park = 371 k | q\* при park = выброс работы сегмента-1 (2.1–2.4 М за шт.) |
|---|---:|---:|---:|
| 25 / 11 | 20 / 272 | **100 %** | 22 % / 35 % |
| 30 / 11 | 12 / 177 | **100 %** | 30 % / 39 % |
| 30 / 13 | 13 / 194 | **100 %** | 21 % / 29 % |
| 40 / 11 | 6 / 89 | **100 %** | 29 % / 39 % |

При оценке park'а в 371 k (цифра самого `workflow.mjs`) механизм переживает **100 % park'ов**:
швов мало (10–20 на прогон), 371 k × 13 = 4.8 М против экономии 5.7–7.8 М — впритык, но в плюсе.
При жёсткой трактовке («park выбрасывает всю работу сегмента-1») порог — **21–39 % промахов**.
Вывод: ветка «обрыв ≠ отказ» **обязательна**, но ей достаточно срабатывать в ~70 % случаев.

### Конструктивная поправка: скриптовая реконструкция handoff'а

Разрыв между жёстким break'ом (E=11.5) и вариантом с файлом (E=7) — это 4.5 хода ≈ **142 k
на шов**. Его можно закрыть **скриптом, а не инструкцией**: после обрыва диспатчить дешёвый
haiku-релей, который собирает handoff из `git diff` + `git status` + последних N строк
отчёта (≈60 k за релей — измеренная средняя цена релея 51–59 k).

| CAP | жёсткий break (E=11.5, H=0) | **гибрид (E=7, H=6k, +60 k на шов)** |
|---:|---:|---:|
| 25 | +10.2 % / +20.2 % | **+12.9 % / +23.7 %** |
| **30** | +10.7 % / +19.5 % | **+12.9 % / +21.6 %** |
| 40 | +8.4 % / +15.3 % | +9.5 % / +16.3 % |

Гибрид возвращает ~2 п.п. прогона и ~2 п.п. корпуса и — в отличие от soft-cap'а — **не
требует от агента ничего**: реконструктор запускает `workflow.mjs`, а не модель по просьбе.

## Self-cap (экономия от p)

Модель: агент **инструктирован** остановиться на CAP, записать
`.mvp/reports/task-NNN.handoff.md` и вернуть `STATUS: PARTIAL`. Шов стоит мои измеренные
**E=7 / H=6 k**. Подчиняется с вероятностью `p`. Начислен налог самой инструкции —
300 токенов на каждый ход каждого агента (1 073 и 10 930 ходов соответственно).

| CAP=30, E=7 | p=10 % | 25 % | 50 % | 75 % | 90 % | 100 % |
|---|---:|---:|---:|---:|---:|---:|
| % прогона | 1.2 | 3.6 | 6.6 | 9.7 | 11.5 | 12.8 |
| % корпуса | 2.8 | 6.8 | 12.6 | 17.8 | 20.4 | 21.9 |

| CAP=25, E=7 | p=10 % | 25 % | 50 % | 75 % | 90 % | 100 % |
|---|---:|---:|---:|---:|---:|---:|
| % прогона | 1.7 | 4.3 | 8.1 | 11.4 | 13.3 | 14.4 |
| % корпуса | 3.8 | 8.2 | 14.6 | 20.4 | 23.0 | 24.6 |

(модель «перепроверка каждые CAP ходов»; при «один шанс на агента» числа ниже на 1–4 п.п.)

**Порог для экономии ≥ 10 %:**

| CAP | прогон `wf_4d14cdc2` | корпус |
|---:|---:|---:|
| 25 | p\* = **65 %** | p\* = **35 %** |
| 30 | p\* = **80 %** | p\* = **40 %** |
| 40 | недостижимо (потолок 9.5 %) | p\* = 60 % |

### Реалистичное p по журналам

Замерил три разных типа дисциплины на всех 1339 workflow-агентах:

| что именно требуется от агента | замер | n |
|---|---:|---:|
| **выходной контракт** (`STATUS:` / `VERDICT:` / `FINDINGS:` / `PATCHES:` в финальном сообщении) | reviewer **98.8 %**, re-review 96.6 %, validator 95.0 %, implementer 94.4 %, fix 93.5 % | 408 |
| **запрет** («`git commit` запрещён» в `_common.md`) | нарушений **0 / 193 = 0.0 %** | 193 |
| **численный самосчётный лимит** («Reply with ONLY … ≤ 15 lines») | нарушений **0 / 49** — но лимит **не связывающий** (медиана 1–2 строки), самосчёт под давлением не проверяет | 49 |
| **остановка, не доделав** (`BLOCKED`/`NEEDS_CONTEXT` разрешены контрактом) | **1 / 193 = 0.5 %** | 193 |
| **вести отчёт по ходу дела** (а не одним куском в конце) | 1 запись медианно, на 97 % жизни; к ходу 30 отчёт есть у **4 %** | 193 |

**Поправка к verdict-3.** Формулировка «история плагина — кладбище доверия к инструкциям»
его же примерами не подтверждается: concerns, `phase=done`, изобретённый флаг `--findings`,
`data` строкой вместо объекта — это отказы **обвязки** (`workflow.mjs`, форматы данных,
релеи), а не несоблюдение контракта моделью. Контракт модель держит на **93.5–98.8 %**,
а связывающий запрет — на 100 %.

**Но для self-cap'а это не та дисциплина.** Он требует двух вещей сразу:
(1) самосчёт ходов — технически возможен (собственные `tool_use` лежат в контексте агента,
так что verdict-3 неточен, когда говорит «нет наблюдаемой величины»: нет *счётчика от
харнесса*, но история своих вызовов у агента есть), эмпирически не проверен ни разу;
(2) остановиться, не доделав — **наблюдаемая базовая частота 0.5 %**.

**Честная вилка p: 0.5 %…95 %, без единого свидетельства выше ~50 %.**
Нижняя граница — единственная прямо релевантная (0.5 % добровольных остановок);
верхняя — соблюдение контракта, который ничего агенту не стоит.
Медиана же поведения «писать по ходу, а не в конце» — 4 %, и это ближе к делу.

## Обновлённые вердикты

### Вариант 1. Жёсткий break (`maxTurns` во фронтматтере + ветка «ответ без `STATUS:` ⇒ продолжение»)

> **CONFIRMED. CAP = 25–30. +10.5 % прогона `wf_4d14cdc2` и +19.5 % workflow-корпуса
> по центру измеренной полосы E; вилка +7.9…+13.6 % прогона / +14.8…+24.3 % корпуса.
> С гибридным реконструктором handoff'а — +12.9 % / +21.6 %.**

- Знак положителен на **всей** измеренной полосе цены возобновления (E = 9…13) при CAP ≥ 25;
  отрицателен только при CAP = 20 и E ≥ 13.
- «+9.0 % убытка» из verdict-3 — **артефакт двойного начисления** (E=13 ходов и `H=60 k`
  одновременно); 397 k D целиком содержатся в ходах разогрева.
- «10.8 % при CAP=30, оптимум 40» из critique-D — артефакт степенной модели; на реальных
  траекториях при том же E=13 CAP=30 даёт больше, чем CAP=40 (+7.9 % против +7.0 % прогона).
- Предпосылки, без которых вердикт недействителен: **B-M1** (свой `agentType`, иначе
  `maxTurns` некуда положить) и ветка «обрыв ≠ отказ» (иначе механизм оплачивается park'ами;
  порог промахов 21–39 %).
- Что осталось непроверенным — то же, что в `verdict-2.md`: сохранность работы за швом.
  Допуск оцифрован: при CAP=30 сегменты могут потратить **до +53 %** ходов сверх плана,
  прежде чем выйти в ноль.

### Вариант 2. Мягкий self-cap (инструкция остановиться и записать handoff)

> **PLAUSIBLE, не подтверждён. Экономия = p × 12.8 % прогона / p × 21.9 % корпуса
> (CAP=30, E=7). Для ≥ 10 % нужно p ≥ 80 % на прогоне и p ≥ 40 % на корпусе.
> Измеренная базовая частота требуемого поведения — 0.5 %.**

- Механизм дёшев и безопасен: налог инструкции 300 ток/ход = 0.4 % корпуса, при p → 0
  он просто ничего не делает. Отрицательного знака нет ни при каком p.
- Но он **строго доминируется вариантом 1** при любом p < 80 % (прогон) / < 90 % (корпус),
  а свидетельств такого p нет.
- Рекомендация: не внедрять как самостоятельный механизм. Если внедрять — то в форме,
  которая не требует остановки: **«держи `.mvp/reports/task-NNN.md` актуальным по ходу»**.
  Это превращает жёсткий break из варианта 1 в гибрид (E 11.5 → 7) и требует дисциплины
  типа «писать», а не типа «остановиться». Текущая базовая частота такого поведения — 4 %,
  так что и её надо мерить пилотом, а не предполагать; и она **не нужна вовсе**, если
  handoff собирает скрипт-релей (+60 k на шов даёт тот же эффект гарантированно).
