## 0. Факт, на котором держится весь раунд (проверен, раньше не предъявлялся)

Прямая проверка полей usage на 189-ходовом агенте, ходы 1–12:

```
ход  base_in  cache_write  cache_read   C_i     C_{i-1}   cache_read / C_{i-1}
 2       2        5 400        37 531   42 933   37 533         1.000
 3       2        5 458        42 931   48 391   42 933         1.000
 …       …            …             …        …        …         1.000
```

**`cache_read(i) = C(i−1)` ровно, с точностью до 2 токенов, 189 ходов подряд, без единого
промаха.** Отсюда две тождественности, а не корреляции:

1. `Σ cache_write за жизнь агента = C_n` (размер ФИНАЛЬНОГО контекста). Каждый токен
   содержания входит в счёт как запись **ровно один раз**.
2. `Σ cache_read = Σ C_i − C_n` — всё остальное есть буквально перечитывание.

Для 189-ходового агента: `C_n = 320 905`, `Σ C_i = 36.70 M`. Значит запись 0.32 M (0.9 %),
чтение 36.38 M (**99.1 %**). Мой тезис перестаёт быть гипотезой: это арифметическое
тождество журнала. Спорить можно только о том, **чьи** токены перечитываются — чем
занят раздел 2.

Кеш при этом **идеально здоров** (hit-rate 1.000 против порога 0.7 из N6 дайджеста).
Возражение «у вас плохо работает кеш» снято: расход не от промахов, а от объёма.

## Вердикты по спорным пунктам (с расчётами)

### Вердикт 1. Угроза N1 («компакция ломает кеш») — механизм выживает в ТОКЕНАХ, но его цена в деньгах вдвое меньше заявленной. Число отзываю и заменяю.

**N1 подтверждён первоисточником дословно.** Anthropic, раздел «Context editing and
prompt caching»:

> **Tool result clearing:** Invalidates cached prompt prefixes when content is cleared.
> To account for this, clear enough tokens to make the cache invalidation worthwhile.
> Use the `clear_at_least` parameter to ensure a minimum number of tokens is cleared each
> time. **You'll incur cache write costs each time content is cleared**, but subsequent
> requests can reuse the newly cached prefix.

И описание самого параметра:

> `clear_at_least` … **This helps determine if context clearing is worth breaking your
> prompt cache.**

То есть Anthropic сам встроил порог «стоит ли ломать кеш» — N1 не гипотеза, а
документированный параметр API.

**Но токены и деньги здесь расходятся, и это надо разделить.** Та же страница даёт
тождество, снимающее двусмысленность:

> `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`

Каждый токен промпта попадает **ровно в одну** категорию. Значит очистка, уменьшающая
промпт, уменьшает и счётчик токенов — всегда, безусловно. **В метрике дискуссии
(токены) N1 мой механизм не опровергает.** Он бьёт по деньгам: перенос токенов из
read (0.1×) в write (1.25×) — это ×12.5 за перенесённый токен.

**Пересчёт в co-design варианте** (триггер на пороге; стабильный префикс `ctx0` живёт
под отдельным `cache_control` и НЕ переписывается — приём из
`docs/.../compaction-threshold`: «The system prompt cache remains valid and is read from
cache; only the compaction summary needs to be written as a new cache entry»; дословный
хвост 30 % накопленного; перестроенный промпт становится новым кешируемым префиксом).
Симуляция проводит очистку по реальным траекториям контекста и **честно начисляет
cache_write на весь переписанный суффикс** (`n1.py`):

Прогон wf_4d14cdc2 (110 агентов, база 72.01 M токенов / 13.69 M цена-ед.*):

| clear @ 200k | 72.01 M | 5.65 M | 66.37 M | 13.69 M | 0.0 % | 0.0 % |
| clear @ 150k | 71.14 M | 5.68 M | 65.45 M | 13.65 M | −1.2 % | −0.3 % |
| clear @ 100k | 60.64 M | 5.92 M | 54.71 M | 12.88 M | −15.8 % | **−6.0 %** |

**Новое честное число вместо прежних «52–68 %»: −68.3 % токенов и −47.2 % цены при
триггере 150k на корпусе; −51.8 % / −36.3 % при консервативном 250k.** Штраф за

Амортизация работает ровно так, как её описывает `clear_at_least`.

**А вот чего делать нельзя — и здесь N1 абсолютно прав.** Симуляция «суммаризатор
переписывает историю каждый ход» (наивная компакция, против которой предостерегает
Harness Effect):

| | токены | cache write | цена-ед. |
|---|---:|---:|---:|
| база | 2763.6 M | 99.0 M | 390.2 M |
| переписывать каждый ход | 2763.6 M (**+0.0 %**) | 2763.6 M | 3454 M (**+785 %**) |

Токенов ровно столько же, счёт в **8.9 раза** больше. Это и есть цена разрушенного
префикса, и я подписываюсь под предостережением. **Моё предписание меняется:
очистка только по порогу с `clear_at_least`, никогда — пошаговая суммаризация.**

**И ещё один вывод, который N1 неожиданно дарит МНЕ.** Сегментация агента (TURN_CAP)
кеш **не ломает вообще**: новый сегмент — это новый суффикс на том же, всё ещё
закешированном префиксе. Замер на wf-прогоне:

| механизм | токены | cache write | Δтокены | Δцена |
|---|---:|---:|---:|---:|
| база | 72.01 M | 5.65 M | — | — |

При почти одинаковой экономии токенов сегментация не добавляет ни одного токена записи,
а очистка добавляет 4.8 %. **Под давлением N1 мой первый механизм (TURN_CAP) становится
сильнее второго (clearing), а не слабее.** Это переупорядочивает мою же программу.

### Вердикт 2. Спор A против B (3.8 % против 32.1 %): оба правы про свой член произведения и оба записывают себе чужое. Каноническое разложение — ниже, двойной счёт снят.

Определения (`canon.py`), используют **только** наблюдаемые поля usage, без моделей:
для агента с контекстами `C_1..C_n` и билетом `P = C_1`, на каждом ходу
`cw_i` = записано в кеш, `cr_i` = прочитано из кеша, `bi_i` = вне кеша.
Билет физически лежит в самом начале префикса, поэтому из `cr_i` его доля — `min(cr_i, P)`.

| № | статья | определение |
|---|---|---|
| 1 | билет, ПЕРВАЯ запись в кеш | `cw_1 + bi_1` |
| 1b | билет, прочитан из кеша СОСЕДНЕГО агента (ход 1) | `cr_1` |
| 2 | билет, перечитывание своим же агентом | `Σ_{i≥2} min(cr_i, P)` |
| 3 | наросшее, первое попадание в контекст | `Σ_{i≥2} (cw_i + bi_i)` |
| 4 | наросшее, ПЕРЕЧИТЫВАНИЕ | `Σ_{i≥2} max(0, cr_i − P)` |
| 5 | output | `Σ out_i` |

Статьи не пересекаются и покрывают всё: `1+3 = cache_write + base_in`,
`1b+2+4 = cache_read`, `5 = output`.

**Прогон wf_4d14cdc2 — сверка сошлась побайтово с shared-facts:**

| статья | токены | % |
|---|---:|---:|
| 1 билет: первая запись в кеш | 1.11 M | **1.5 %** |
| 1b билет: прочитан из кеша соседа | 1.65 M | 2.3 % |
| 2 билет: перечитывание своим агентом | 20.65 M | **28.4 %** |
| 3 наросшее: первое попадание | 2.89 M | 4.0 % |
| 4 наросшее: ПЕРЕЧИТЫВАНИЕ | **45.72 M** | **62.8 %** |
| 5 output | 0.80 M | 1.1 % |

Контроль: `1+3 = 4.00 M` против `cache_creation 3 995 364 + base 3 042` ✓;
`1b+2+4 = 68.01 M` против `cache_read 68 013 693` ✓; `5 = 800 128` ✓.

**Все три проекта (1541 сущность, 2779.6 M):** 1 → 27.85 M (1.0 %); 1b → 13.31 M (0.5 %);
2 → 560.0 M (20.1 %); 3 → 75.56 M (2.7 %); **4 → 2085.0 M (75.0 %)**; 5 → 17.97 M (0.6 %).

**Вердикт по принадлежности:**

- **Статья 1 (1.5 %) — безраздельно B.** Но B заявлял её как 3.8 %; из этих 3.8 %
  **больше половины (2.3 п.п.) — это статья 1b: билет, который агент не записывал, а
  прочитал из кеша, оставленного соседним агентом той же роли.** Prompt caching
  амортизирует билет **между** агентами, а не только внутри. Реально уплаченный один
  раз билет прогона — **1.11 M = 1.5 %**, а не 3.8 %.
- **Статья 2 (28.4 % / 20.1 %) — ничья, и записывать её себе целиком не вправе никто.**
  Это произведение `P × (n−1)`. Частные производные: `∂/∂P = (n−1)` — рычаг B;
  `∂/∂n = P` — рычаг C. Обе производные ненулевые, ни одна не доминирует.
  **Каноническое правило, которое я предлагаю принять всем четверым: каждый вправе
  записать себе не долю статьи, а только `Δ`, который производит его собственное
  изменение, и при совместном применении экономии перемножаются, а не складываются:**
  `save(ΔP, Δn) = P·n − (P−ΔP)(n−Δn)`, что строго **меньше** `ΔP·n + P·Δn` на `ΔP·Δn`.
  Числом: B режет билет ревьюера 32.3k → 16.3k (ΔP = 16.0k), C режет средние ходы
  ревьюера 13.8 → 10 (Δn = 3.8). Порознь: B = 16.0k × 13.8 × 31 агент = 6.85 M;
  C = 32.3k × 3.8 × 31 = 3.81 M; сумма 10.66 M. Совместно: 31 × (32.3·13.8 − 16.3·10) k
  = **8.77 M.** Двойной счёт = **1.89 M = 2.6 % прогона**, и он ровно `ΔP·Δn·N`.
- **Статья 3 (4.0 % / 2.7 %) — D.** Это объём содержания, который задача реально
  требует прочитать. Единственная статья, где «сложность задачи» — прямая причина.
  Мой М2 (читать диапазонами, не файлами целиком) режет именно её, и это единственное
  место, где я и D работаем по одному объекту.
- **Статья 4 (62.8 % / 75.0 %) — безраздельно C.** Ни A, ни B, ни D не предложили
  ни одного механизма, который её трогает. A трогает её косвенно (меньше ходов
  ревьюера → меньше перечитываний), но его собственный анализ этого не называет.
- **Статья 5 (1.1 % / 0.6 %) — ничья и неинтересна.**

**Следствие для формулировки A «обвязка — 50 % прогона» и D «имплементер — 73 %»:**
обе верны как разбиение по РОЛЯМ и обе ортогональны этому разбиению по СТАТЬЯМ.
Роль отвечает на вопрос «кто потратил», статья — «на что». Складывать проценты из
разных разбиений нельзя, и в раунде 1 это делали все, включая меня.

**Уточнение моего собственного числа.** «78 % избытка над полом» из раунда 1
разлагается как статьи 3+4+5 = 2.7 + 75.0 + 0.6 = **78.3 %** — арифметически то же
самое, но имя было неточным. Правильное имя: **из всего корпуса 75.0 % — это
перечитывание содержания, которое агент уже один раз прочитал, и ещё 20.1 % —
перечитывание билета. Впервые в контекст попадает 3.7 % токенов, наружу выходит 0.6 %.**

## Атаки

### Атака на D: порог «≥50 запросов» — это мой TURN_CAP, только с самым дорогим из возможных хэндоверов. На датасете D мой вариант выигрывает.

D и я разделяем физику (его показатель 1.67 — моя статья 4) и оба предлагаем **резать
длину разговора имплементера**. Отличие ровно одно: **где проходит шов и сколько стоит
передача через него.**

- D режет по границе ЗАДАЧИ → каждая половинка платит **полную новую лестницу**:
  +7 tool-диспатчей (7 × 58 854 = 412 k) + ревьюеров заново. D сам оценивает шов
  в **0.9 M токенов**.
- Я режу по границе ХОДА внутри одной задачи → шов стоит `E` ходов переориентации
  плюс чтение handoff-файла. Лестница не дублируется вообще.

**Прямое сравнение на датасете D (`d_wfagents.json`, 124 задачи, 851.2 M), его же
степенной моделью `6950·req^1.67` и `6313·req^1.60`:**

| механизм | параметр | экономия |
|---|---|---:|
| D: разбить задачу | порог 100 | 4.1 % / 3.1 % |
| D: разбить задачу | порог 60 | 12.1 % / 6.8 % |
| **D: разбить задачу** | **порог 50 (его рекомендация)** | **18.0 % / 9.1 %** |
| D: разбить задачу | порог 40 | 21.6 % / **8.6 %** ← пессимист УЖЕ падает |
| D: разбить задачу | порог 30 | 24.4 % / **8.4 %** |
| C: TURN_CAP=50, E=2 | | **16.2 %** |
| C: TURN_CAP=40, E=2 | | **20.4 %** |
| **C: TURN_CAP=30, E=2** | | **26.2 %** |
| C: TURN_CAP=30, E=3 | | 23.3 % |
| C: TURN_CAP=20, E=2 | | 33.8 % |

(у D два столбца — «ревьюер дешевеет с пакетом» / «ревьюер платится дважды»)

**Три вывода.**

1. **При его же порогах я даю больше.** CAP=30 → 26.2 % против лучшего D 18.0 % и его
   реалистичного 9.1 %.
2. **Структурное различие видно в форме кривой.** У D в пессимистичном режиме экономия
   имеет **максимум на пороге 50 и дальше падает** (18.0 → 8.6 → 8.4 %), потому что
   каждая новая задача покупает новую лестницу. У меня кривая **монотонна** (11.0 →
   16.2 → 20.4 → 26.2 → 33.8 %), потому что новый сегмент лестницу не покупает.
   D сам это признаёт в своём риске: «правило должно быть порогом, а не «дроби как
   можно мельче»». Моё правило не имеет такого ограничения — и это прямое следствие
   более дешёвого шва.
3. **Его единственный контраргумент — «цена хэндовера у C не измерена» — теперь
   оцифрован как условие.** Break-even, посчитанный на его же данных:

   | CAP | C перестаёт бить D-оптимиста (18.0 %) при | C перестаёт бить D-пессимиста (9.1 %) при |
   |---|---|---|
   | 50 | E ≥ 1 | E ≥ 7 |
   | 40 | E ≥ 4 | E ≥ 8 |
   | **30** | **E ≥ 5** | **E ≥ 8** |
   | 25 | E ≥ 6 | E ≥ 8 |

   **При CAP=30 я проигрываю его лучшему сценарию, только если переориентация нового
   сегмента стоит 5+ лишних ходов, и его реалистичному — только если 8+.**
   На реальных дельтах 189-ходового агента (не по модели) я мерил E=2 и E=3 —
   и это было консервативное допущение, а не измерение. **Спор между C и D сводится
   к одному неизвестному числу E, и я называю его эксперимент: взять 3 задачи
   с имплементером > 60 запросов, прогнать с `TURN_CAP=30` и handoff-файлом,
   посчитать фактическое число ходов сегментов-продолжений. Если E < 5 — D проиграл.**

Отдельно: D пишет «C целится в меньший член: 48 % дисперсии на ходы, 19 % на контекст
на ход». Это верно **про дисперсию** и неверно **про уровень**. Мой механизм целится
не в `ctx/req` — он целится ровно в `n_req` (TURN_CAP), то есть в тот самый член 48 %,
который D называет главным. Мы целимся в один и тот же множитель; расходимся только в
цене шва.

### Атака на A: его потолок ревьюера и мой TURN_CAP — НЕ подмножества. Пересечение ровно ноль, и это проверяемо.

Я предполагал, что A частично дублирует меня. **Проверил — не дублирует нигде.**

| **A + C совместно** | 54.41 M | **24.4 %** |
| A + C агрессивно (рев 15 + ролевые 20) | 49.20 M | 31.7 % |

`5.9 % + 18.6 % = 24.4 %`, совместно ровно **24.4 %**, **пересечение 0.000 п.п.,
пересечение по агентам — 0 из 9 и 7.** Это единственная пара механизмов в дискуссии,
которую складывать честно можно, и я это фиксирую в пользу A.

**Но природа экономий разная, и A должен это назвать.** Мой replay воспроизводит его
4.53 M почти точно — у меня 4.23 M (5.9 %), расхождение 7 % от методики. Однако:
**A свои ходы УДАЛЯЕТ (ревьюер упирается в потолок и обязан вернуть `CANNOT_VERIFY` —
работа теряется), а я свои ПЕРЕНОШУ (сегмент продолжает ту же работу).**
Это не одинаковые 6 % и 19 %: у A экономия оплачена риском потерянной находки
(его же данные: minor'ы в 013 и 016 пришли с опросов на 17 и 22 хода — то есть
из зоны за потолком), у меня — риском потерянного контекста при передаче.

И встречный упрёк по его главному тезису: A пишет, что «собственная квадратика C
работает против её предписания — C логически требует больше диспатчей, а не меньше,
и тем самым оправдывает лестницу». **Это верно и это не возражение — это моё
предписание.** Я никогда не требовал меньше агентов; я требую меньше *ходов на агента*
при сохранении суммарной работы, и ровно это делает сегментация. A сам приходит к тому
же выводу в своём §5 («удалять ходы, а не сливать агентов») и в слабости №6
(«правильная формулировка A — убрать ходы внутри ступени, а это фактически частный
случай C»). **Принимаю эту капитуляцию и фиксирую: спор A против C закончен слиянием,
механизмы складываются без остатка.**

### Атака на B: его 32.1 % держатся на моём множителе, и его собственный «естественный эксперимент» это доказывает.

B строит всё на инварианте: доля налога 32.1 % в mvp-пайплайне против 31.0 % в SDD
при семикратной разнице формы. **Инвариант настоящий, но он доказывает мою позицию,
а не его.** Статья 2 = `P·(n−1)`. Её доля в общем счёте =
`P(n−1) / (P·n + наросшее)`. Она остаётся ~31 % при разной `n` ровно потому, что
наросшее растёт пропорционально `n` — то есть **инвариантность доли налога есть
следствие линейного роста контекста, моего механизма.** B нашёл мою константу и
назвал её своей.

Проверка на разложении: доля билета внутри всего перечитывания —
**31.1 % в wf, 31.3 % в SDD, 21.1 % по корпусу.** Первые два совпали (это его
инвариант), третий — нет. Различает их одно: в корпусе есть 19 долгожителей
с n ≥ 100, у которых наросшее давит билет. **Инвариант B держится только там, где
нет долгожителей; там, где они есть, его доля падает с 31 % до 21 %, а моя растёт
с 69 % до 79 %.** Инвариант — не закон, а артефакт выборки без длинных хвостов.

Второе. B: «C без B саморазрушается: 500 короткоживущих агентов × 2P = 24 M = 33 %».
Расчёт неверен по двум причинам, обе измеримы:
(а) он берёт `2P` как цену, но **статья 1b доказывает, что второй и последующие агенты
одной роли билет не записывают, а читают из кеша соседа** — в wf-прогоне 1.65 M из
2.75 M «билетов» (60 %) пришли как cache_read по цене 0.1×. Его 500 агентов заплатят
не 500 записей, а 1 запись + 499 чтений.
(б) моя сегментация не создаёт 500 агентов взамен 110 — она превращает 7 агентов
в 26, а замер cache_write при этом: **5.65 M → 5.64 M, то есть не меняется вообще**
(таблица в Вердикте 1). Его «дно, ниже которого C не опускается» на реальных данных
не наблюдается.

Третье и решающее. B сам признаёт (слабость №3): «самая дорогая роль прогона —
implementer, 49.9 %, и у неё самый дешёвый билет, 14 % своей стоимости. Половину
прогона мой лом не берёт вообще. Потолок всех моих механизмов — ~15 %.»
**В канонических статьях это читается так: B владеет 1.5 % безраздельно и спорит за
долю в 28.4 %, которую может двигать только вместе со мной. Я владею 62.8 %
безраздельно.** Порядок операций, который он предлагает («сначала тонкий префикс,
потом декомпозиция»), я принимаю — он не конфликтует, и произведение считается
по формуле из Вердикта 2, а не сложением.

## Что отзываю

1. **Отзываю число «52–68 % от чистки tool-результатов» как заявку об экономии.**
   Оно было посчитано только в токенах. С учётом инвалидации кеша (N1, подтверждён
   дословной цитатой Anthropic) честная пара: **−68.3 % токенов / −47.2 % цены**
   при триггере 150k и **−51.8 % / −36.3 %** при консервативном 250k. Экономия
   осталась, но треть её съедается cache_write — это надо было сказать сразу.

2. **Отзываю формулировку «ранний компакт» из предписания раунда 1.** Заменяю на
   «очистка tool-результатов по порогу с `clear_at_least`, стабильный системный префикс
   под отдельным `cache_control`». Пошаговая суммаризация истории на моих же данных
   даёт **+785 % к счёту при нулевой экономии токенов** — я бы предложил механизм,
   который делает хуже, если бы N1 не поймал.

3. **Отзываю «78 % избытка» как самостоятельное число.** Оно корректно, но его имя
   было неточным и оно перекрывалось с чужими статьями. Заменяю каноническим
   разложением: **статья 4 (перечитывание наросшего) = 62.8 % прогона wf и 75.0 %
   корпуса — вот моя неоспариваемая доля.**

4. **Отзываю формулировку «квадратично» в сильном виде.** Внутри агента — да
   (R² = 0.987 на линейность контекста). Межагентно показатель 1.39, а на срезе

   срез даёт 1.15.

5. **Отзываю подозрение, что механизм A дублирует мой.** Проверил: пересечение
   0.000 п.п. и 0 агентов. Механизмы складываются.

## Обновлённые механизмы (число, % прогона, риск)

Порядок изменён по итогам N1: сегментация выходит на первое место, потому что она
единственная кеш-нейтральна.

### М1 (был М1, усилен). `TURN_CAP` в `workflow.mjs` + продолжение через handoff-файл

**Где.** `skills/build/workflow.mjs:1709` — `dispatchAgentText(implPrompt, …)` запускает
ролевого агента без ограничения по ходам. Добавить `TURN_CAP`; агент на пределе пишет
`.mvp/reports/task-NNN.handoff.md` и завершается статусом `CONTINUE`; `runOneTask`
диспатчит продолжение с тем же boundary и ссылкой на handoff.

**Число.** На wf_4d14cdc2 (реальные траектории, H = 6k, E = 2):
**CAP=30 → −13.37 M = −18.6 % токенов, −9.8 % цены; cache_write не меняется
(5.65 → 5.64 M).**
На датасете D (124 задачи, 851.2 M, его степенная модель): **CAP=30, E=2 → −26.2 %**;
E=3 → −23.3 %.
Покрытие: трогает 100 из 162 имплементеров (90.3 % токенов роли) и 7 из 31 fix-агента.

**Риск.** Handoff — лоссовый канал; Anthropic мерил: после компакции high-level факты
3/3, obscure specifics 0/3. Ломается на отладочных задачах с длинной цепочкой
отвергнутых гипотез — продолжение повторит уже сделанные ошибки. Митигация: в handoff
обязателен раздел «что пробовал и почему не подошло». **Неизвестная величина —
E (лишние ходы на переориентацию); при E ≥ 5 механизм проигрывает варианту D.**
Эксперимент назван выше.

### М2 (был М3, пересчитан и переформулирован). Очистка tool-результатов по порогу, co-design с кешем

**Где.** Диспатч субагентов и главный цикл. Триггер 150–200k вместо дефолтного
авто-компакта на ~967k (модели с 1M-окном), `clear_at_least` не ниже 30k,
`cache_control` в конце системного префикса, `exclude_tools` для Edit/Write.

**Число.** Корпус (2763.6 M): **триггер 150k → −68.3 % токенов / −47.2 % цены**
(133 события очистки, cache_write +3.8 %); консервативный 250k → **−51.8 % / −36.3 %**.
На одном wf-прогоне эффект мал (триггер 150k → −1.2 %), потому что там почти никто не
доходит до 150k: **механизм адресован долгожителям, а не лестнице.**

**Риск.** Очистка невосстановима. Для ревьюера, обязанного цитировать конкретную строку
(`quote` в FINDINGS), очистка нужного результата ломает контракт — но ревьюеры живут
медиану 8 ходов и до порога не доходят (max 27 за всю историю), механизм их не
касается. **Главный риск — реализационный: если вместо порогового clearing сделать
пошаговую суммаризацию, счёт вырастет в 8.9 раза при нулевой экономии токенов.**

### М3 (был М2, понижен). Запрет чтения файлов целиком

**Где.** `skills/build/agents/*.md`: `grep -n` по символу → `sed -n 'A,Bp'` по
диапазону; `cat` целого файла только для файлов < 150 строк. Источник проблемы —
инструкция auto-режима «read files with cat, head, or sed -n … rather than using the
dedicated Read tool»: `cat` не имеет лимита, Read имеет.

**Число.** 84.6 % сырого объёма tool-результатов прогона — дампы целых файлов
(Read 60.0 % + bash `cat` 24.6 %), усиленно 24.1 M = 33.5 % прогона. Сокращение объёма
вдвое → **−12.0 M = −16.6 % токенов**; пессимистично (−30 % объёма) → −10.0 %.
В канонических статьях бьёт по статье 3 и по её вкладу в статью 4.

**Риск.** Неполная картина файла → правка мимо соседнего инварианта → лишний
fix-раунд (0.3–0.5 M каждый в этом прогоне; по D — 2.25× цены задачи). Три лишних
fix-раунда на 8 задач съедают половину экономии. Правило обязано быть
«диапазон ПОСЛЕ grep», а не «первые 100 строк», и не распространяться на
файлы-контракты (`capabilities.ts`, `manifest.schema.json`).

### Совместный эффект, посчитанный без двойного счёта

На wf_4d14cdc2, реальные траектории: **М1 (CAP=30) + механизм A (потолок ревьюера 15)
= 24.4 %, пересечение ровно 0.000 п.п.** Добавление М3 к ним считать сложением нельзя
(он режет содержание, которое М1 уже частично перестаёт перечитывать) — верхняя
граница тройки ≈ **32–35 % прогона**, и это оценка, а не замер.
На корпусе решает М2: **−47.2 % цены / −68.3 % токенов.**

## Источники раунда 2 (дословные цитаты проверены по первоисточнику)

1. **Context editing** — https://platform.claude.com/docs/en/build-with-claude/context-editing
   «**Tool result clearing:** Invalidates cached prompt prefixes when content is cleared.
   To account for this, clear enough tokens to make the cache invalidation worthwhile.
   Use the `clear_at_least` parameter… You'll incur cache write costs each time content
   is cleared, but subsequent requests can reuse the newly cached prefix.»
   `clear_at_least`: «This helps determine if context clearing is worth breaking your
   prompt cache.» — N1 подтверждён дословно.

2. **Prompt caching** — https://platform.claude.com/docs/en/build-with-claude/prompt-caching
   «Prompt caching references the entire prompt - `tools`, `system`, and `messages`
   (in that order)»; «the cache follows the hierarchy: `tools` → `system` → `messages`.
   Changes at each level invalidate that level and all subsequent levels»;
   «Because the hash is cumulative… changing any block at or before the breakpoint
   produces a different hash on the next request»;
   множители: «5-minute cache write tokens are 1.25 times… 1-hour cache write tokens
   are 2 times… Cache read tokens are 0.1 times the base input tokens price».
   Тождество без двойного счёта: «`total_input_tokens = cache_read_input_tokens +
   cache_creation_input_tokens + input_tokens`».

3. **Compaction at a token threshold** —
   https://platform.claude.com/docs/en/build-with-claude/compaction-threshold
   «To maximize cache hit rates, add a `cache_control` breakpoint at the end of your
   system prompt… The system prompt cache remains valid and is read from cache;
   Only the compaction summary needs to be written as a new cache entry.»
   — это и есть co-design, которого требует N1.

4. **Managing context** — https://claude.com/blog/context-management — «reducing token
   consumption by 84%» на 100-ходовом eval; моя симуляция при триггере 100k даёт
   −81.4 % токенов (расхождение 2.6 п.п.).

5. **Model config** — https://code.claude.com/docs/en/model-config — авто-компакт
   моделей с 1M-окном «at about 967K tokens by default»; наш наблюдённый пик 755k,
   то есть дефолт до нас не дотягивается ни разу.

6. **Harness Effect**, N1/C1/C2/C3 дайджеста — https://arxiv.org/abs/2607.06906 —
   антагонизм компакции и кеша, `p_eff ≈ p_in·(1 − h + h·κ)`, Θ(k²) → Θ(k).
