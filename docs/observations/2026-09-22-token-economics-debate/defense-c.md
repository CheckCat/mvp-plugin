## n1.py — признание

### Баг мой, воспроизведён, подписываю

Скептик прав до строчки. Вот виновный код, мой собственный (`n1.py`):

```python
d=[ctx[i]-ctx[i-1] for i in range(1,n)]     # дельты РЕАЛЬНОЙ траектории
c=c0
for k in range(n):
    if c>T: c=c0+keep*(c-c0)                # моя симулированная очистка
    ...
    if k<n-1: c+=d[k]                        # <-- d[k] бывает ОТРИЦАТЕЛЬНОЙ
```

`d[k] < 0` там, где харнесс **уже** авто-компактнул. После собственной симулированной
очистки счётчик вычитает падение ещё раз и уходит в минус. Прогнал свой же симулятор
с подсчётом отрицательных ходов:

| популяция | сущностей | ходов | **ходов с c < 0** | минимум ctx | сумма токенов |
|---|---:|---:|---:|---:|---:|
| `main` | 14 | 4 371 | **1 566** | **−788 889** | **−312.1 M** (!) |
| `sub` | 195 | 5 339 | 0 | 0 | 466.5 M |
| `wf` | 1 339 | 10 930 | 0 | 0 | 742.0 M |

Главные циклы дали **отрицательный «расход»**, и именно из этой отрицательной суммы
вырос мой «−68.3 %». Скептик насчитал 1 562 хода и минимум −788 889 — у меня 1 566 и
ровно тот же минимум (расхождение в 4 хода — в `sub` попали два агента, порождённые
самой этой дискуссией).

### Его исправление проверено независимой реализацией

Я не стал пересчитывать его скриптом. Написал свой (`n1fix.py`) по его же описанию модели:
симулированный контекст = реальный минус то, что сняли МЫ; никогда ниже стабильного
префикса; реальное падение харнесса **уменьшает пул удаляемого**, а не уводит счётчик
в минус:

```python
pool = max(0, real_ctx - c0)
if removed > pool: removed = pool     # харнесс уже забрал часть — нельзя снять её дважды
sim = max(c0, real_ctx - removed)
if sim > T: cut = (sim-c0)*(1-keep); removed += cut; sim -= cut
```

| T | мои токены | мой Δ | **его Δ** | моя цена | **его цена** | мои clears | его clears |
|---|---:|---:|---:|---:|---:|---:|---:|
| 250k | 2 098.0 M | −24.9 % | **−25.1 %** | −18.0 % | **−18.2 %** | 48 | 47 |
| **150k** | **1 681.2 M** | **−39.9 %** | **−39.9 %** | **−27.9 %** | **−28.1 %** | 186 | 182 |
| 100k | 1 320.5 M | −52.8 % | **−52.8 %** | −36.4 % | **−36.5 %** | 532 | 521 |

Разложение по популяциям при T=150k у меня: `main` 823.0 M (**73.9 %** эффекта),
`sub` 175.8 M (15.8 %), `wf` 115.2 M (10.3 %) — у него 74.3 / 15.3 / 10.4 %.
Сошлось везде в пределах половины процентного пункта.

> **Подписываю. Честная пара — «−39.9 % токенов / −27.9 % цены» вместо моих
> «−68.3 % / −47.2 %». Завышение 1.7×, и причина — арифметический баг в моём коде,
> а не спорная трактовка.**

Подписываю и второе, более неприятное: **как механизм плагина чистка контекста
не существует.** `clear_tool_uses_20250919` — бета-заголовок Messages API, в Claude Code
никуда не прокинут; `autoCompactWindow` — пользовательская настройка сессии. 89.7 %
эффекта (`main`+`sub`) плагину недоступны. Оставшиеся 10.3 % (`wf`) недоступны тоже —
инструмента нет.

Что я **не** отзываю: сам факт остаётся крупнейшим числом дискуссии, просто он не наш.
`autoCompactWindow: 150000` в `settings.json` оператора даёт **823.0 M = 29.4 % всего
корпуса трёх проектов** — больше, чем все плагинные механизмы вместе (−13…−18 %).
Это вывод дискуссии, но строка не в плагине, и записывать её в смету плагина нельзя.
Моя ошибка была не в том, что я нашёл этот эффект, а в том, что я приписал его механизму.

## Реализуемый CAP (конструкция, дисциплина, расчёт с E=7)

### Что именно сломано, и что НЕ сломано

Проверил по бинарю сам, не по чужому пересказу. Подтверждаю вердикт-3 дословно:

```js
if (Ir.attachment.type === "max_turns_reached") {
  T(`[Agent: ${e.agentType}] Reached max turns limit (${Ir.attachment.maxTurns})`);
  break
}
```

`break` — **финального хода нет**. Подтверждено и со стороны SDK: при `maxTurns`
результат — `ResultMessage` с `subtype: "error_max_turns"`, поле `result` недоступно.
И `agent(prompt, opts)` Workflow-тула действительно не имеет `maxTurns` — строка описания
из бинаря: `opts?: {label?, phase?, schema?, model?, effort?, isolation?, agentType?}`.

**Мой протокол «упёрся → пишу handoff → возвращаю CONTINUE» в буквальном виде
нереализуем. Отзываю его.**

Но вилка вердикта-3 («handoff и enforcement взаимно исключают друг друга») построена на
двух невысказанных допущениях, и оба неверны:

1. *«Агент не видит счётчика ходов»* — верно, но **хук видит**. На stdin хука приходят
   `session_id`, `transcript_path`, `cwd`, **`subagent_id`** («Present only when the hook
   fires from within a subagent… Absent for the main thread»). Встроенного счётчика нет,
   но `transcript_path` позволяет посчитать. Наблюдаемая величина существует — просто не
   у модели, а у хука.
2. *«Единственный потолок — `maxTurns`»* — неверно. `hooks` есть **во фронтматтере
   субагента**, областью действия — только этот субагент. А `PreToolUse` с
   `permissionDecision: "deny"` **не обрывает цикл**: модель получает сообщение
   «Permission for this tool use was denied… Try a different approach» и **следующий ход**.

То есть остановка с ходом на запись handoff'а возможна — не через `maxTurns`, а через
хук, который начинает отказывать в инструментах.

### Дисциплина следования инструкциям — измерено по журналам, а не предположено

Скептик пишет: «история плагина — это кладбище доверия к инструкциям». Проверил числом.
Все workflow-агенты трёх проектов (1 339), роль определена по первому user-сообщению.

| что за инструкция | класс | соблюдение |
|---|---|---:|
| «Reply with ONLY the following, **≤ 15 lines total**» (`implementer.md:90`) | числовой лимит в **одном** действии | **193 / 193 = 100 %** (медиана факта — 3 строки, max 9) |
| строка `STATUS:` в финальном ответе | формат в одном действии | 182 / 193 = **94.3 %** |
| `FINDINGS:` строго одной строкой валидного JSON | формат в одном действии | 190 / 195 = **97.4 %** |
| строка `VERDICT:` | формат в одном действии | 164 / 195 = 84.1 % |
| «`validate-task.sh` already ran this project's CI mirror… **Do not re-run the suite**» (`reviewer.md:41`) | **процессный запрет**, проверяем в одном действии | 177 / 195 = **90.8 %** (18 ревьюеров перезапустили: `ci-mirror.sh` ×12, `npm test` ×3, `pytest` ×2, `jest` ×1) |
| «do not re-run git commands yourself» (`reviewer.md:15`) | процессный запрет | 25 git-вызовов из 2 094 = **98.8 %** |
| **`STATUS: BLOCKED` — единственный существующий канал «остановись, не доделав»** | **добровольная остановка при незавершённой работе** | **1 / 193 = 0.5 %** |

Вывод точнее, чем «кладбище»: **формат агенты держат отлично (94–100 %), процессные
запреты — хорошо (91–99 %), а добровольно не доделывать — не умеют вовсе.**
Для справки: `DONE_WITH_CONCERNS` — 41 / 193 = 21.2 %, то есть нестандартные ветки
статуса агенты используют охотно; не используют именно **остановку**.

Это и есть честный приор для мягкого self-cap'а: он требует ровно того единственного
поведения, которого в журналах 0.5 %. Мой механизм в мягком виде бьёт в самое слабое
место измеренной дисциплины, и я это фиксирую до того, как считать его экономику.

### Цена шва: почему «+9.0 % убытка» вердикта-3 посчитан не по тому числу

Вердикт-3 считал по `E = 13 ходов, H ≈ 397 k` (число D). Вердикт-2 измерил E напрямую
и разложил: **E = 7 ходов (95 % ДИ 4–9), ≈ 220 k на шов**, а из 13 ходов D 36 % — «новая
земля», которую неразрезанный агент прошёл бы всё равно. Контроль вердикта-2, который
решает спор: **холодный имплементер без предшественника — 13 ходов и 649 k**, то есть
*дороже* fix-агента (12 ходов / 403 k). 13 ходов — это цена запуска ЛЮБОГО агента,
а не налог продолжения.

И ключевое, чего не заметили обе стороны: **E = 7 измерено на популяциях, у которых
handoff-файла НЕ БЫЛО.** RETRY-имплементер получает список нарушений в промпте,
fix-агент — findings; у обоих работа предшественника лежит на диске и в
`.mvp/reports/task-<id>.md`, но связного «что пробовал и почему не подошло» нет ни у кого.
Класс **B** классификатора вердикта-2 называется буквально «повторное добывание того,
что **МОГЛО** быть в handoff» — то есть E = 7 **уже включает** цену отсутствия handoff'а.

> **Следствие: E = 7 — это параметр варианта «жёсткий обрыв без handoff-файла»,
> а не варианта с ним. Тот вариант, который вердикт-3 объявил неработающим по цене,
> — единственный, для которого цена измерена напрямую.**

### Вариант 1 — мягкий self-cap (инструкция «остановись после ~N вызовов»)

**Конструкция.** В `skills/build/agents/implementer.md` (и `fix.md`) — блок: «После
примерно N инструментальных вызовов остановись, даже если работа не закончена. Запиши
`{{REPORT_PATH%.md}}.handoff.md`: что сделано, что осталось, какие файлы трогал, что
пробовал и почему не подошло. Ответь `STATUS: PARTIAL`.» В `workflow.mjs:1710–1748` —
ветка: `PARTIAL` ⇒ диспатч продолжения с путём handoff'а. Правок ~15 строк, ничего
в харнессе не нужно.

**Экономика.** Полная выгода при идеальном соблюдении (CAP=30, E=7, H=6k, мой реплей
реальных траекторий прогона `wf_4d14cdc2`) — **14.1 % прогона** (вердикт-2: 13.8 %,
расхождение 0.3 п.п. — реплеи независимые).
Носимая цена: блок ~300 токенов лежит в файле роли, то есть в префиксе, и перечитывается
на каждом ходу ролевого агента. Ролевых агентов в прогоне 15, их ходов 551 →
**165 k = 0.23 % прогона**. Ложный `PARTIAL` (агент объявил остановку, хотя закончил) —
один лишний диспатч ≈ 14 k билета + 7 ходов разогрева × 31.5 k = **235 k за случай**.

| p (доля реально остановившихся) | fp = 0 | fp = 5.7 % | fp = 20 % |
|---|---:|---:|---:|
| 0.05 | +0.48 % | +0.20 % | −0.50 % |
| 0.20 | +2.60 % | +2.32 % | +1.62 % |
| 0.50 | +6.84 % | +6.56 % | +5.86 % |
| 0.80 | +11.08 % | +10.80 % | +10.10 % |

**Безубыточная доля соблюдения — p ≥ 1.6 %.** Механизм почти невозможно сделать
убыточным: носимая инструкция стоит 0.23 %, а одно сработавшее прерывание у
73-ходового агента окупает её многократно.

**Но ожидаемое p низкое.** Приор из журналов — 0.5 % (единственный существующий канал
добровольной остановки). Оптимистичный приор — 90.8 % (соблюдение процессных запретов),
но он не переносится: те запреты проверяются **в одном действии**, а здесь нужно
поддерживать счётчик через 30 ходов и остановиться при незавершённой работе.
Честная оценка: **p где-то между 5 % и 40 %, то есть +0.5…+5 % прогона.**

**Вердикт по варианту 1: реализуем, почти бесплатен, но его ожидание — единицы процентов,
а не 14 %. Как самостоятельный механизм слаб; как страховка поверх варианта 2 — полезен.**

### Вариант 2 — жёсткий `maxTurns` + восстановление из дерева (без handoff-файла)

**Конструкция.** `maxTurns: 30` во фронтматтере ролевого агента (требует B-M1 —
собственные файлы агентов; для ролевых они уже есть, их собирает `mvp:bootstrap`).
Харнесс обрывает без финального хода → ответ без `STATUS:` → **новая ветка** в
`runOneTask` (`workflow.mjs:1710–1748`, между `dispatchAgentText` и `parseStatus`):
ответ без `STATUS:` **и** непустой `git status` по boundary ⇒ это обрыв по потолку,
диспатчить продолжение, а не park. Пустой `git status` ⇒ прежнее поведение (park).
Дискриминатор реальный: обрыв по потолку всегда оставляет правки в дереве,
а «агент не понял задачу» — нет.

Handoff изобретать не нужно — состояние уже на диске: рабочее дерево + обязательный
`.mvp/reports/task-<id>.md` (контракт `_common.md`). Гейты не ломаются: `finalize()`
коммитит только в конце, `review-package.sh` диффит BASE против рабочего дерева
(design note 10), `park()` делает `git stash push -u`, не destructive reset — это
вердикт-3 проверил сам, и я с ним согласен.

**Экономика — мой реплей реальных траекторий, E = 7 (измерено вердиктом-2 именно на
этой конфигурации), H = 0 (файла нет, перечитывание уже внутри E):**

| CAP | прогон `wf_4d14cdc2` (72.0 M) | весь wf-корпус (857.2 M) | швов в прогоне |
|---:|---:|---:|---:|
| 20 | **+19.4 %** | +32.6 % | 31 |
| **25** | **+18.0 %** | **+29.5 %** | 19 |
| **30** | **+16.1 %** | **+25.8 %** | 10 |
| 40 | +11.3 % | +18.7 % | 5 |
| 50 | +7.1 % | +12.3 % | 4 |

(для сравнения — тот же реплей с H = 6 000, как считал вердикт-2: CAP=30 → 14.1 %
прогона, CAP=25 → 15.1 %. Вариант 2 выходит на 2 п.п. лучше именно потому, что не платит
за handoff-файл дважды.)

Запас прочности из вердикта-2: break-even E при CAP=30 — **16 ходов на прогоне и 19 на
корпусе** против измеренных 7 (ДИ 4–9). Сегменты-продолжения могут потратить на +53 %

даёт +6.1 % прогона — то есть «+9.0 % убытка» вердикта-3 не воспроизводится и при
его собственном параметре; расхождение в модели шва (он начисляет и H=397 k, и E=13,
тогда как 397 k — это и есть денежное выражение тех же 13 ходов).

**Риски, честно.**
- Молчаливая потеря «obscure specifics». Вердикт-3 прав, что пайплайн ловит именно их.
  Но вариант 2 — это ровно та конфигурация, в которой уже 40 раз работали RETRY- и
  fix-агенты этого пайплайна, и их результаты проходили ревью. Это не гипотеза.
- Если ветку-дискриминатор не сделать, каждое срабатывание потолка — park ценой ~371 k.
  При 10 швах в прогоне это 3.7 M = 5.1 % — экономия сокращается втрое. **Ветка
  обязательна, без неё механизм внедрять нельзя.**
- `maxTurns` живёт в файле агента ⇒ адресности нет, потолок плоский. Вердикт-2 показал,
  что она и не нужна: плоский CAP=30 трогает 8 % агентов, держащих 68 % токенов.

### Вариант 3 — co-design: мягкий сигнал через хук + жёсткий `maxTurns` как страховка

Это ответ на вилку вердикта-3, и он собирается из того, что в сборке уже есть.

**Конструкция.**
1. Во фронтматтере ролевого агента — `hooks: PreToolUse` (матчер `Bash|Read|Grep|Glob`),
   команда-счётчик. Хук получает `subagent_id` и `transcript_path`, считает ходы этого
   субагента по транскрипту. Пока count < N — `allow`.
2. При count ≥ N хук возвращает `permissionDecision: "deny"`. Модель получает
   «Permission for this tool use was denied… Try a different approach» **и следующий ход**
   (цикл не обрывается — проверено). `Write` и `Edit` остаются разрешёнными.
3. Семантика отказа **предзагружена**: в теле файла роли (то есть в префиксе с первого
   хода) написано: «Если тебе начали отказывать в Bash/Read — это сигнал исчерпания
   бюджета. Немедленно запиши handoff в `<path>` и ответь `STATUS: PARTIAL`.»
   Канал `permissionDecisionReason` до модели не доходит — он и не нужен, значение
   отказа согласовано заранее.
4. Страховка: `maxTurns: N + 8` в том же фронтматтере. Если агент проигнорировал сигнал —
   жёсткий обрыв, и срабатывает ветка варианта 2.

**Почему это снимает вилку.** Вердикт-3 прав, что `maxTurns` и handoff исключают друг
друга. Но хук — это третья точка: он **наблюдает** счётчик (которого нет у модели) и
**не обрывает** цикл (в отличие от `maxTurns`). Оба условия, которые вердикт-3 назвал
несовместимыми, выполняются одновременно.

**Экономика.** Верхняя граница = вариант 1 при p → 1, то есть **14.1 % прогона**
(с handoff'ом шов дешевле: класс B вердикта-2 — 4 хода из 7 — это ровно то, что handoff
устраняет; при E = 3 вместо 7 CAP=30 даёт ~16.5 %). Нижняя граница = вариант 2
(**16.1 %**), потому что страховка `maxTurns` срабатывает всегда. **То есть вариант 3
имеет гарантированный пол варианта 2 и потолок выше него.**

**Риск и что не проверено.** Реакция модели на серию отказов не измерена ни разу —
она может начать «пробовать другой подход» (как ей прямо предлагает текст отказа)
вместо записи handoff'а, сжигая оставшиеся 8 ходов. Это единственное неизвестное,
и оно ограничено сверху: худший случай = вариант 2 (страховка). Плюс правка сложнее:
скрипт хука + счётчик по транскрипту + сборка хука в шаблон агента
(`assemble-agent.sh`, `verify-agents-drift.sh`, `plugin-lock`).

### Сравнение и что предписываю

> **Предписываю В2.** Он единственный, у которого цена шва измерена именно на его
> конфигурации (RETRY + fix, n=38, E=7, ДИ 4–9), не зависит от дисциплины модели вовсе
> и имеет запас прочности 2.3× до точки безубыточности. **CAP = 25–30** (maximin

>

> каждое срабатывание — кандидат на park ценой ~371 k, и механизм съедает себя.

**Что отзываю в этом раунде:**
1. Число «−68.3 % / −47.2 %» — баг вычитания реального авто-компакта поверх
   симулированной очистки. Заменяю на **−39.9 % / −27.9 %**.
2. Претензию, что чистка контекста — **механизм плагина**. Она харнесс-уровня целиком.
3. Протокол «агент упирается в потолок → пишет handoff → `CONTINUE`» в буквальном виде.
   Харнесс делает `break` без финального хода — проверено по бинарю.
4. Трактовку статьи 1b («кеш соседа той же роли») — это общий харнесс-префикс.
5. Допущение E = 2. Измеренное E = 7; на моих числах это −2.5 п.п. к CAP=30, не более.

**Что усиливаю:**
1. **TURN_CAP реализуем и выживает при измеренной цене шва.** Вердикт-3 объявил его
   нереализуемым по конструкции и убыточным по экономике; первое верно только для моей
   первоначальной формулировки (суррогат он сам же и описал), второе посчитано по
   параметру D (E=13 / 397 k), который вердикт-2 опроверг измерением и контролем
   («холодный старт 13 ходов / 649 k» — то есть 13 ходов платит любой агент, а не только
   продолжение).
2. **E = 7 измерено именно на конфигурации «без handoff-файла»** (RETRY + fix, n=38) —
   то есть на варианте В2, который я и предписываю. Это единственный механизм всей
   дискуссии, у которого критический параметр измерен на своей собственной конфигурации.
3. **Дисциплина следования инструкциям в пайплайне измерена**, а не предположена:
   формат — 94–100 %, процессные запреты — 91–99 %, добровольная остановка — **0.5 %**.
   Это одновременно объясняет, почему мягкий вариант слаб, и почему жёсткий не зависит
   от этой слабости.
4. **Вилка «handoff против enforcement» разрешима** — через `hooks` во фронтматтере
   субагента (`subagent_id` + `transcript_path` дают счётчик хуку; `PreToolUse` deny не
   обрывает цикл и оставляет модели ход). Не предписываю без замера, но фиксирую как
   конструкцию.
