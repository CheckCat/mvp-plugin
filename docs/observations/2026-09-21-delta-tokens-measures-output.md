# `delta_tokens` измеряет output-токены всего прогона, а не «взгляд контроллера»

Дата: 2026-09-21. Источник: прогон `wf_4d14cdc2-05c` пайплайна на проекте
trellis (задачи 011–018, 8 задач, 110 субагентов, один Workflow-run).

## Что утверждалось до сих пор

Четыре места плагина согласованно говорили одно и то же:

- `lib/plan-io.mjs`: «`delta_tokens` is budget.spent() as seen by the
  CONTROLLER only — measured against the workflow runtime's own records it
  understates true cost by ~8.4x, because subagent usage is invisible to it»;
- `skills/build/workflow.mjs`: то же, как обоснование существования
  `dispatches`;
- `skills/retro/SKILL.md`: «взгляд контроллера, субагентов не видит»;
- `docs/specs/2026-08-21-mvp-pipeline-v2-design.md` §A.6: «Измеренное
  занижение `delta_tokens` против фактических записей рантайма — 8.4×»;
- телеметрия писала это в сам факт: `controller_only: true`.

## Метод

Журнал прогона (`subagents/workflows/wf_4d14cdc2-05c/agent-*.jsonl`) содержит
поле `usage` на каждое сообщение модели. Одна и та же строка запроса
встречается несколько раз: частичный ответ несёт `output_tokens: 1`, финальный
— настоящее число, при одинаковом `requestId`. Поэтому суммировать подряд
нельзя, берётся МАКСИМУМ на пару `(файл, requestId)`.

Первая попытка этого не учитывала и дала 63 094 output-токена — занижение в
12.7 раз. Число выглядело правдоподобно и подтверждало бы старую версию;
ошибка нашлась только потому, что не сходилась ни с чем другим.

## Числа

| величина | значение |
|---|---|
| уникальных запросов | 1 073 |
| `output_tokens`, все 110 субагентов | **800 128** |
| `input_tokens` | 3 042 |
| `cache_creation_input_tokens` | 3 995 364 |
| `cache_read_input_tokens` | 68 013 693 |
| output + input + cache_creation | 4 798 534 |
| сумма `delta_tokens` задач 011–018 | **783 887** |
| `subagent_tokens` из task-notification | 5 645 985 |

## Вывод

`delta_tokens` и суммарный `output_tokens` субагентов сходятся с точностью
~2 % (783 887 против 800 128). Это одна величина. Значит `budget.spent()`
субагентов ВИДИТ — ровно как написано в документации инструмента Workflow:
«output tokens spent this turn across the main loop and all workflows».

Он считает только **output**. А `subagent_tokens` из уведомления — полный
расход, в котором output составляет 14 %, а доминирует создание кэша
(3 995 364 против 800 128).

Отсюда «занижение в 8.4×» — это отношение output-only к полному расходу, то
есть сравнение двух разных величин, а не потеря субагентов. Соотношение
устойчиво (на этом прогоне 7.2×) именно потому, что доля output в полном
расходе примерно постоянна, — и ровно поэтому его легко принять за
подтверждённый коэффициент недоучёта.

## Что это меняет

- `controller_only: true` — неверное утверждение о собственных данных.
  Прекращено для новых событий; в старых остаётся, `events.jsonl` append-only.
- `dispatches` остаётся лучшим доступным прокси стоимости, но по другой
  причине, чем записано: он коррелирует не с output, а с созданием кэша,
  которое и есть основная масса расхода.
- Стоимость прогона берётся из `subagent_tokens` в уведомлении о завершении
  Workflow. Внутри `workflow.mjs` этой величины нет и быть не может.

## Осталось неизвестным

Чему точно равен `subagent_tokens`: 5 645 985 против 4 798 534 (output +
input + cache_creation) — 85 %, простой суммой из журнала не воспроизводится.
Ни одно решение в плагине на это не опирается, поэтому вопрос оставлен
открытым, а не додуман.
