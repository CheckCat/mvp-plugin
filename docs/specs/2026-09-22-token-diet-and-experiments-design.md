# Токенная диета пайплайна + реестр самопроверяемых гипотез

Дата: 2026-09-22. Статус: черновик на ревью оператора.
Основание: `docs/observations/2026-09-22-token-economics.md` (смета и константы)
и `docs/observations/2026-09-22-token-economics-debate/final-verdict.md`
(вердикты, места в коде). Числа в этой спеке не передоказываются — они
CONFIRMED дискуссией; спека определяет, как их внедрить и как плагин сам
доберёт недостающие доказательства.

## 1. Проблема

91% токенов прогона — перечитывание контекста; дефолтный `workflow-subagent`
несёт префикс 24–33k при 6 реально используемых инструментах (ролевой — 14–15k);
длинные опросы ревью находок не дают (все находки ≤15 ходов); 7% агентов держат
63% токенов. Подтверждённая смета: Tier 1 −13%, Tier 2 −18%, Tier 3 (CAP) до
−25% — но Tier 3 не сдан без эксперимента о сохранности работы, и все оценки
контрфактические. Отдельная проблема: незакрытые гипотезы после дискуссий
копятся в головах и observation-файлах и не проверяются никогда.

## 2. Решение одним абзацем

Плагин получает (а) узкие ролевые агенты для механики пайплайна
(reviewer/validator/relay) с ограниченным набором инструментов и `maxTurns` —
это Tier 1+2; (б) реестр открытых гипотез с решающими порогами и жизненным
циклом, который `mvp:retro` сверяет с журналами каждого прогона; (в) режим
`experiments` (greedy на альфе), в котором `mvp:build` может применять
экспериментальный рукав (CAP=30) к срезу задач ВНУТРИ обычного прогона —
никогда не дублируя прогон. Подтверждённая гипотеза превращается в правку
плагина руками (Iron Law ретро сохраняется).

## 3. Границы

- Вне спеки: harness-механизмы (`autoCompactWindow` — решение оператора,
  задокументировано в observation), цены моделей, выбор моделей ролей.
- `REVIEW_SAMPLES=3` не трогается (снятие гейта, не экономия — см. кладбище).
- Метрика приёмки — токены по журналам (дедуп по requestId), считает скрипт,
  не LLM.

## 4. Ролевые агенты механики пайплайна (Tier 1: B-M1 + B-M2)

Три новых шаблона в `skills/bootstrap/templates/` (стек-независимые):

| шаблон | tools во фронтматтере | maxTurns | кто на нём работает |
|---|---|---|---|
| `mvp-reviewer.template.md` | Read, Bash | 15 | опросы ревью и re-review |
| `mvp-validator.template.md` | Read, Bash | 15 | validate-шаги лестницы |
| `mvp-relay.template.md` | Bash | 3 | все relay/relayLine |

Содержимое — существующие промпт-контракты этих ролей (сейчас живут в тексте
диспатч-промптов `workflow.mjs`) + `_common.md` НЕ включается (механика
пайплайна не пишет код проекта; контракт границы задачи ей не нужен — это
и есть главная диета). Фронтматтер: `name`, `description`, `tools`, `maxTurns`.

Сборка: `skills/bootstrap/SKILL.md` Шаг 4 собирает их безусловно, тем же
`assemble-agent.sh` (шаблон без стека — существующий fallback-путь). Enum
плановых ролей НЕ расширяется: это не роли плана, ревьюер не может быть
`planned_role`. `assemble-agent.sh` штампует их в plugin-lock как derived —
механизм уже есть, `mvp:sync` подхватывает без правок.

`workflow.mjs`: диспатчи ревьюера/re-review — внутри `runReviewLadder()`
(опрос, ретрай на неразборчивом FINDINGS, re-review после fix); валидатора —
внутри `runValidateLadder()`; `callOpts` обоих релеев — внутри `relay()` и
`relayLine()` (литерал `agentType: 'mvp-relay'` в каждой). Все получают
`agentType: "mvp-reviewer" | "mvp-validator" | "mvp-relay"`. Больше в
диспатчах не меняется ничего.

Важно про регистрацию: агенты читаются харнессом на старте сессии. После
bootstrap/sync с новыми ролями прогон `mvp:build` требует новой сессии — это
уже задокументированное свойство (см. plugin-lock spec), правило не новое.

## 5. Диета `_common.md` (Tier 1: B-M3)

Из `_common.md` режется только проза-обоснование принципов (~3.5k токенов);
НЕ трогаются: контракт границы задачи, формат отчёта/STATUS, правила
Stop&Ask/blockers.md — три задачи trellis прошли ревью корректно именно на
этом контракте. Правка идёт диффом в спеке плана (точный список абзацев),
чтобы ревьюер задачи мог проверить «режем прозу, не контракт».

## 6. Ветка «обрыв ≠ отказ» для ревью (Tier 2: A-M1)

`maxTurns: 15` обрывает опрос без финального хода → сейчас `parseStatus`
вернёт BLOCKED → park. Новая ветка в `runReviewLadder`:

- опрос вернул null/без STATUS **и** файл findings этого опроса существует и
  парсится → опрос засчитан с этими findings;
- файла нет → опрос засчитан как «воздержался» (в ladder-агрегации не голос,
  а пропуск), лестница продолжает оставшиеся опросы;
- park из-за одного оборванного опроса запрещён; park остаётся возможен по
  прежним причинам (неполный пакет, CANNOT_VERIFY-правила не меняются).

## 7. Реестр гипотез

`docs/experiments/registry.json` в репо плагина — источник истины, правится
только руками (коммитом). Формат:

```json
{ "version": 1, "max_open": 5,
  "hypotheses": [ {
    "id": "H1-cap-work-preservation",
    "title": "CAP=30 не теряет работу за швом",
    "status": "needs-optin",          // open | needs-optin | confirmed | refuted | expired
    "mode_required": "greedy",         // greedy | passive
    "check_script": "scripts/experiments/h1-cap.sh",
    "threshold": "человекочитаемое решающее правило с числом",
    "ttl_runs": 10, "opened": "2026-09-22"
  } ] }
```

Правила гигиены (enforced скриптом, не дисциплиной):
- регистрация новой гипотезы (`lib/experiments.sh add`) отклоняется без
  `threshold` с числом, при `open+needs-optin >= max_open`, и молча — никогда;
- `runs_seen` инкрементируется на каждом прогоне, где check_script получил
  данные; `runs_seen >= ttl_runs` без вердикта → статус `expired` (кандидат
  на закрытие, проверки прекращаются);
- `confirmed|refuted|expired` — терминальные: retro печатает «перенеси в
  observation и удали из реестра» до тех пор, пока строка не исчезнет.

Результаты замеров — append-only в ПРОЕКТЕ: `.mvp/experiments/results.jsonl`
(`{hypothesis, run_id, value, verdict, ts}`); check_script пишет туда сам.
Обновление статуса в registry.json — руками в репо плагина (retro говорит
что и куда), потому что установка может быть marketplace-кэшем: писать в кэш
= потерять при переустановке. `runs_seen` тоже выводится из results.jsonl
(число уникальных run_id), а не хранится как мутируемое поле — registry.json
меняется ТОЛЬКО при смене статуса.

`lib/experiments.sh` (verbs, JSON-контракт как у всех lib):
- `list` — реестр + вычисленные runs_seen/статусы-кандидаты;
- `check <run_id>` — прогоняет check_script каждой открытой гипотезы, чей
  mode совместим с флагом; пишет results.jsonl; выводит сводку;
- `add --json '{...}'` — валидация и вставка (для будущих гипотез).

Учёт токенов для check-скриптов: `scripts/experiments/tokcost.py` — перенос
проверенного модуля из дискуссии (дедуп по (файл, requestId), максимум по
полю). Журналы субагентов: `~/.claude/projects/<slug>/<session>/subagents/`.

## 8. Флаг experiments и инвариант недублирования

`.mvp/state.json`, ключ `experiments`: `greedy | passive | off`.
Отсутствует → `greedy` (альфа). Меняется оператором (`state.sh set`).

- `off`: реестр игнорируется целиком (ни check, ни рукавов);
- `passive`: retro выполняет `check` по журналам; build ничего не меняет;
- `greedy`: как passive + build может применять экспериментальный рукав
  к срезу задач внутри прогона.

**Инвариант (закон, проверяется тестом): ни один режим не порождает
дополнительный прогон, диспатч или задачу.** Greedy-рукав только меняет
параметры диспатчей задач, которые и так исполняются. Максимум один активный
рукав на прогон; срез — задачи с чётным порядковым номером исполнения
(детерминированно, воспроизводимо, даёт внутрипрогонный контроль).

## 9. Экспериментальный рукав CAP (greedy, до сдачи Tier 3)

Пока `H1-cap-work-preservation` открыта и режим greedy:

1. Bootstrap/sync дополнительно создаёт `<role>-capped.md` для ролей
   имплементеров: копия собранного `<role>.md` + `maxTurns: 30` во
   фронтматтере (делает `assemble-agent.sh` тем же прогоном; в plugin-lock
   штампуется как derived — иначе `mvp:sync` сочтёт их чужими).
2. `workflow.mjs`: задача из чётного среза диспатчит имплементера с
   `agentType: "<role>-capped"`; нечётные — контроль, без изменений.
   Файла capped-роли нет (флаг включили после bootstrap, sync не гоняли) →
   рукав молча неактивен, вся задача идёт контролем — рукав никогда не
   диспатчит несуществующую роль.
3. Ветка-дискриминатор в `runOneTask` (вокруг локальной константы
   `CAP_SEGMENTS`): результат имплементера null/без STATUS **и** `git status`
   непуст → это обрыв по потолку, не отказ:
   `lib/handoff.sh` (новый) собирает указатель — `git status --short`,
   `git diff` (cap по размеру), путь брифа, номер сегмента — в
   `.mvp/handoff-<task>.md`, и диспатчится продолжение той же capped-ролью
   с этим файлом. Лимит 4 сегмента на задачу, дальше — обычный park.
   Дерево чисто при обрыве → это НЕ потолок, обычная обработка отказа.
4. Телеметрия задачи получает поля `arm: "cap30"|"control"`, `segments: N` —
   их пишет finalize-контур, как пишет dispatches.

`scripts/experiments/h1-cap.sh` считает по results/журналам/телеметрии:
- доля задач рукава, дошедших до finalize без park — не ниже контроля;
- findings ревью на задачу рукава — не выше контроля;
- фактические токены рукава против контроля (tokcost) и суммарные лишние
  ходы сегментов ≤ +53% (порог безубыточности из вердикта).
Вердикт при ≥8 задачах в рукаве суммарно по прогонам (можно накапливать
между прогонами — results.jsonl это уже хранит). Порог не добран за
ttl_runs=10 прогонов → expired.

По `confirmed`: CAP=30 включается по умолчанию (maxTurns в основные шаблоны
ролей, рукав и capped-копии удаляются) — отдельным коммитом руками.
По `refuted`: рукав и capped-копии удаляются, вердикт в observation.

## 13. Порядок внедрения и приёмка

1. Реестр + флаг + retro-шаг (механизм наблюдения раньше механизмов диеты —
   чтобы H2 мог замерить эффект Tier 1+2 с первого же прогона).
2. Tier 1+2 одним шагом (роли рождаются сразу с maxTurns, relay, диета,
   ветка ревью) — H2 меряет их совокупный эффект (−17.9%), раздельная
   атрибуция не нужна.
3. Рукав CAP (greedy) — включается сам при первом подходящем прогоне.
Приёмка каждого шага — журнальный замер скриптом, не самоотчёт агента.

## 14. Риски

- Ролевые агенты требуют новой сессии после сборки — известное свойство,
  на нём уже стоит plugin-lock; риск не новый.
- Ветки «обрыв ≠ отказ» опираются на эвристику (STATUS/дерево/файл findings);
  цена промаха дискриминатора — выброс сегмента (~2.0M), допуск до 52%
  промахов; ветка с чистым деревом никогда не маскирует настоящий отказ.
- H1 может не добрать 8 задач за ttl — тогда честный expired, CAP не
  внедряется на неподтверждённых числах.
- Смена поведения харнесса (семантика maxTurns, ленивые схемы) — H3
  дежурит именно над этим.
