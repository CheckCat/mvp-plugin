# plugin-lock + mvp:sync — актуализация артефактов проекта при обновлении плагина

Дата: 2026-09-21
Статус: дизайн принят, не реализован

## 1. Проблема

Плагин порождает в проекте файлы, но проект не помнит, от какого состояния
плагина он их получил. Связь односторонняя и незаписанная: `mvp:bootstrap`
собирает `.claude/agents/*.md` из `skills/bootstrap/templates/`, и на этом
след обрывается. Плагин потом меняется — проект об этом не узнаёт никогда.

Симптом на 2026-09-21: в `trellis` после правок `_common.md` и шаблона
devops `verify-agents-drift.sh` даёт 5/5 нарушений, и ни один гейт пайплайна
этого не видит, потому что drift-check вызывается только внутри
`mvp:bootstrap` — то есть ровно один раз, в момент, когда дрейфа ещё не
может быть по построению.

Цена ошибки известна и измерена: устаревшие агенты не регистрируются,
задачи уходят на `general-purpose` без контракта `_common.md`, и ревью это
пропускает, потому что судит дифф, а не автора. Так прошли три задачи
подряд (`skills/bootstrap/SKILL.md`, HARD-GATE).

Второй симптом того же класса — изменившееся требование, которое не
порождает файл. Правило e2e-изоляции добавлено в
`devops-engineer.docker-compose.fastify.template.md`, обязательный раздел
`## Not executed` — в `_common.md`. Проект, собранный до этих правок, не
получает их ни при каких условиях и ничего о них не знает.

## 2. Решение одним предложением

Проект получает lock-файл с хэшами тех файлов плагина, от которых он
зависит; `lib/plugin-lock.sh check` сравнивает его с текущим плагином;
производное чинится пересборкой, непроизводное — докладывается оператору;
гейт `mvp:build` не пускает прогон на устаревших агентах.

## 3. Область

Плагин порождает в проекте четыре сорта файлов, и механизм трактует их
по-разному.

**Производные** — `.claude/agents/<role>.md`. Собираются механически
(`assemble-agent.sh`: фронтматтер шаблона роли + `_common.md` целиком +
тело шаблона + подстановка плейсхолдеров). Своего содержимого не имеют,
поэтому пересборка ничего не теряет. **Отслеживаются, чинятся автоматически.**

**Нормативные** — `skills/*/SKILL.md`, `skills/*/scripts/*`, `lib/*`.
Это файлы плагина, а не проекта; они не порождают артефакт, но задают
требования, которым проектные файлы обязаны удовлетворять.
**Отслеживаются, только докладываются.**

**Проектные** — `CLAUDE.md`, `docs/architecture.md`, `.mvp/invariants.md`,
`.mvp/ci-mirror.sh`. Рождаются на bootstrap по мотивам брифа, дальше живут
как обычный код проекта. **Не отслеживаются вообще.**

Про `ci-mirror.sh` отдельно, потому что соблазн его отслеживать сильный.
Bootstrap генерирует его по маппингу «стек → команды»: для fastify это пять
строк с guard'ами. В `trellis` он вырос до 206 строк тремя коммитами, и
каждый — реакция на инцидент: одноразовый Postgres перед `npm run test`
(`3602ff5`), БД-тесты в CI (`79970ab`), запрет врать зелёным, когда проба
готовности смотрела во внутренний unix-сокет контейнера, а строка
подключения — на `127.0.0.1:<port>` (`8f78350`). Пять сгенерированных строк
до сих пор лежат в нём внизу нетронутыми; всё, что выше, маппинг не может
знать в принципе. Перегенерация такого файла не экономит работу, а
уничтожает её. То же верно для `CLAUDE.md` и `invariants.md`: их
расхождение с шаблоном — норма, а не дефект.

**Состояние** — `.mvp/plan.json`, `.mvp/state.json`, `.mvp/ledger.md`.
Схема этих файлов версий не имеет, миграций нет. **Вне области этого
дизайна.** Явно отложено: проблем этого класса пока не возникало, и
закладывать версионирование схемы до первого настоящего разрыва — работа
наперёд.

## 4. Формат `.mvp/plugin-lock.json`

Коммитится вместе с проектом.

```json
{
  "lock_version": 1,
  "plugin": {
    "name": "mvp",
    "version": "2.0.0",
    "git_sha": "81dc3cb1f4e2a90d3c5b7e8f2a1d4c6b9e0f3a2d"
  },
  "derived": {
    ".claude/agents/devops-engineer.md": {
      "role": "devops-engineer",
      "stack": "docker-compose.fastify",
      "template": "devops-engineer.docker-compose.fastify.template.md",
      "placeholders": {
        "PROJECT": "trellis",
        "SERVICE_API": "trellis-api",
        "SERVICE_WORKER": "trellis-worker"
      },
      "sources": {
        "skills/bootstrap/templates/_common.md": "sha256:…",
        "skills/bootstrap/templates/devops-engineer.docker-compose.fastify.template.md": "sha256:…"
      },
      "output_sha256": "sha256:…"
    }
  },
  "normative": {
    "skills/bootstrap/SKILL.md": "sha256:…",
    "lib/validate-task.sh": "sha256:…"
  }
}
```

### 4.1. Почему хэши, а не версия

`plugin.version` и `plugin.git_sha` записываются, но гейт по ним не судит.
Semver требует дисциплины бумпа, а дисциплина уже нарушена: `version` стоит
на `2.0.0` поверх одиннадцати коммитов правок шаблонов и скиллов. `git_sha`
недоступен, если плагин установлен из кэша маркетплейса, где нет `.git`, и
врёт при незакоммиченных правках в репозитории плагина.

Хэш содержимого не требует ничего и работает одинаково в обоих способах
установки. Единственное назначение `git_sha` — дать `mvp:sync` возможность
показать настоящий `git diff` по изменившимся файлам, когда плагин доступен
как чекаут. Недоступен — печатается только список путей.

### 4.2. Почему `derived` ключуется путём результата

Сравнивать надо то, что реально лежит в проекте, а не то, что мы думаем про
роли. Ключ — путь артефакта; `role`/`stack`/`template`/`placeholders` внутри
записи существуют ровно затем, чтобы пересборка была воспроизводима
байт-в-байт.

Это необходимо: собранный `.claude/agents/<role>.md` **не помнит, из какого
шаблона собран**. `name` и `description` копируются из шаблона, но нет поля,
контрактно несущего `<role>.<stack>` — только свободный текст `description`.
Для части ролей он называет фреймворк прямо (`devops-engineer.docker-compose.fastify`
и `devops-engineer.docker-dokploy.nestjs`, например, различимы текстуально —
«docker-compose» против «Dokploy deploy config»), но это не контракт:
разбор прозы обратно в точный `<role>.<stack>` — эвристика человека, а не
парсинг схемы, и на новом или отредактированном шаблоне она молча ошибается.
Плюс `devops-engineer.docker-dokploy.fastapi.template.md` использует
плейсхолдеры, а `assemble-agent.sh` берёт `PROJECT` по умолчанию из имени
директории проекта — значение, которое вызывающий мог переопределить через
env и которое нигде не сохраняется.

### 4.3. `output_sha256`

Хэш самого собранного файла. Ловит вторую половину задачи: расхождение в
`sources` означает «плагин уехал», расхождение в `output_sha256` при чистых
`sources` означает «файл правили руками» — прямое нарушение правила из
`mvp:bootstrap` («НЕ правь `.claude/agents/*.md` руками»). Два разных
диагноза, и они не должны маскировать друг друга.

Существующий `verify-agents-drift.sh` ловит только подмену `_common.md`
(byte-substring-инвариант); тело роли не проверяет никто.

### 4.4. Состав `normative`

Задаётся глобами в `lib/plugin-lock.sh`, не списком в конфиге:

```
skills/*/SKILL.md
skills/*/scripts/*
lib/*
```

Глоб самоподдерживающийся — новый файл плагина попадает под наблюдение сам.
Список был бы третьим источником правды рядом с кодом и шаблонами и начал
бы врать с того дня, когда кто-то забудет его обновить.

Намеренно снаружи:
- `skills/*/agents/*` и `skills/*/references/*` — меняют поведение плагина,
  но не требуют изменений в проекте;
- `docs/`, `tests/`, `.claude-plugin/` — к проекту отношения не имеют.

## 5. `lib/plugin-lock.sh`

Единственный владелец формата lock-файла. Контракт вывода — как у всех
скриптов плагина: последняя строка stdout это
`{"ok","reason","hint","data"}`, `ok:false` всегда выходит 1.

Запускается из корня ЦЕЛЕВОГО ПРОЕКТА. Путь к плагину — от расположения
самого скрипта (`BASH_SOURCE`), как в `assemble-agent.sh`.

### 5.1. `record <role> <stack>`

Upsert одной записи в `derived`. Вычисляет `sources`, `output_sha256`,
фиксирует `template` и фактические значения плейсхолдеров. Не трогает
записи других ролей и секцию `normative`. Создаёт lock-файл, если его нет.

Зовётся только из `assemble-agent.sh`, снаружи не нужен.

### 5.2. `check`

Чистая диагностика, ничего не пишет. `data`:

```json
{
  "lock_present": true,
  "derived_stale":     [{"path": "…", "role": "…", "stack": "…",
                         "changed_sources": ["…"]}],
  "derived_tampered":  [{"path": "…", "role": "…", "stack": "…"}],
  "derived_missing":   [{"path": "…", "role": "…"}],
  "normative_changed": ["…"],
  "normative_added":   ["…"],
  "normative_removed": ["…"]
}
```

- `derived_stale` — расходятся `sources`;
- `derived_tampered` — расходится `output_sha256` при чистых `sources`;
- `derived_missing` — запись в lock есть, файла в проекте нет.

`check` возвращает `ok:false` на **любое** расхождение, включая расхождение
только в нормативке. Он диагност, а не политика: что с находкой делать,
решает вызывающий (§7).

Отсутствие lock-файла при наличии `.claude/agents/*.md` — отдельный
`reason` (`no plugin-lock.json`), не смешанный с дрейфом: это не «проект
устарел», а «сравнить не с чем».

### 5.3. `seal`

Переписывает секцию `normative` хэшами текущего плагина. Секцию `derived`
не трогает.

Отдельный явный акт со смыслом «оператор прочитал, что изменилось в
нормативке, и принял это». Никогда не вызывается автоматически из гейта:
иначе печать становится бессмысленной, она молча догоняла бы плагин.

## 6. Изменения в `assemble-agent.sh`

После `mv "$TMP" "$OUT"` — вызов `lib/plugin-lock.sh record <role> <stack>`.

Почему производитель штампует сам: он единственный, кто одновременно знает
роль, выбранный шаблон, значения плейсхолдеров и путь результата — все
четыре факта, нужные для пересборки. Сейчас он их вычисляет и выбрасывает.
Это же убирает класс расхождений «собрали агента, забыли отметить»: отметка
становится частью сборки, а не отдельным шагом, который можно пропустить.

Контракт вывода `assemble-agent.sh` не меняется. Провал `record` — это
`ok:false` с `reason` про lock; агент при этом уже записан, и повторный
запуск идемпотентен.

## 7. Политика: гейт в `lib/gate.sh build`

`gate.sh build` дополнительно зовёт `plugin-lock.sh check` и разводит
случаи. Ниже `ok` — результат **самого гейта**, не результат `check`:
`check` возвращает `ok:false` на любое расхождение (§5.2), и гейт его
переинтерпретирует.

**Расхождение в `derived` (`stale`/`tampered`/`missing`) → гейт даёт
`ok:false`, halt.** `reason` называет роли, `hint` — `run mvp:sync`. Сюда
же попадает `lock_present: false` при наличии `.claude/agents/*.md`.

**Расхождение только в `normative` → гейт даёт `ok:true`**, плюс
`normative_changed` в `data`. `skills/build/SKILL.md` обязан показать
список одной строкой.

Обоснование асимметрии. Нормативка не блокирует, потому что иначе любой
коммит в плагин останавливает все проекты сразу, и первое, чему научится
оператор — обходить гейт; гейт, срабатывающий не по делу, живёт до второго
срабатывания. `derived` блокирует жёстко, потому что цена известна и
измерена (§1): три задачи на `general-purpose`, все три одобрены ревью.

Остальные гейты (`brief`, `clarify`, `bootstrap`, `plan`) не трогаются:
агентов они не диспатчат, и блокировать их дрейфом агентов незачем.

## 8. Скилл `mvp:sync`

`skills/sync/SKILL.md`. Терминальный, `NEXT` отсутствует.

Iron Law: **чинится только производное; нормативка докладывается, но
никогда не применяется автоматически.**

```
Шаг 1. plugin-lock.sh check
Шаг 2. ok:true → «всё актуально», стоп.
Шаг 3. lock отсутствует (lock_present:false) → Stop&Ask: перечислить роли
       из .claude/agents/, предложить стеки из `## Stack` брифа, дождаться
       подтверждения. Не угадывать: стек не хранится машинно-читаемо,
       угадывание по description — эвристика, её ошибка молча даёт не
       того агента.
Шаг 4. роли для пересборки: lock отсутствовал на Шаге 3 → derived_stale/
       derived_tampered/derived_missing пусты по построению, берётся весь
       список, подтверждённый на Шаге 3; иначе — сами эти три массива
       (для derived_missing стек не известен — спросить как на Шаге 3).
       На каждую → assemble-agent.sh <role> <stack>  (он же обновит запись
       в lock)
Шаг 5. verify-agents-drift.sh — подтверждение
Шаг 6. показать normative_changed / added / removed; если git_sha в lock
       есть и плагин — git-чекаут, показать `git diff <sha>..HEAD -- <пути>`
Шаг 7. Stop&Ask по нормативке: требует ли изменение правок в проекте.
       Требует — это отдельная работа, не работа sync'а:
       plan-io.mjs add-task.
Шаг 8. plugin-lock.sh seal — только после подтверждения оператора
Шаг 9. finalize.sh sync <msg-file>
```

HARD-GATE: если на Шаге 4 пересобран хоть один агент — дословное требование
перезапустить сессию перед `mvp:build`, теми же словами, что в
`mvp:bootstrap`.

Шаг 7 — единственное место, где скилл думает, а не двигает данные, и он же
место, где механизм честно упирается в свой предел. `mvp:sync` не умеет и не
должен уметь решать, что новое правило e2e-изоляции означает для
`tests/e2e/helpers/compose.ts`. Он гарантирует, что оператор это правило
увидит.

### 8.1. Rationalization table (в SKILL.md)

| Соблазн | Почему нет |
|---|---|
| «Нормативка изменилась не сильно, запечатаю без чтения» | печать — это заявление «я прочитал и принял»; `seal` без чтения превращает механизм в тихого догонялу плагина |
| «Подправлю `.claude/agents/*.md` руками, там одна строка» | `output_sha256` это поймает и назовёт `tampered`; правится шаблон в плагине, потом пересборка |
| «Стек роли не записан, но я его помню» | Шаг 3 — Stop&Ask; неверный стек собирает не того агента и ничем себя не выдаёт |
| «Перегенерирую заодно `ci-mirror.sh`, он же тоже из шаблона» | §3: пять строк маппинга внутри 206 строк проектного кода; перегенерация уничтожает работу трёх инцидентных коммитов |

## 9. Изменения в `lib/finalize.sh`

Новый пресет scope:

```
sync = .claude/agents .mvp/plugin-lock.json
```

`VALID_SCOPES` дополняется значением `sync`.

Почему не переиспользовать `bootstrap`: тот стейджит
`CLAUDE.md docs/architecture.md .claude/agents .mvp` — слишком широко для
sync'а, затянул бы в коммит несвязанные грязные файлы.

## 10. Изменения в `mvp:bootstrap`

Шаг 4 не меняется текстом: `record` происходит внутри `assemble-agent.sh`.

Шаг 7 дополняется вызовом `lib/plugin-lock.sh seal` перед `finalize.sh` —
первичная печать нормативки. Пресет `bootstrap` уже стейджит `.mvp`
целиком, так что `plugin-lock.json` попадает в bootstrap-коммит без правки
пресета.

## 11. Тесты

`tests/lib/plugin-lock.test.sh`. Негативный контроль обязателен на каждый
случай: после написания теста код ломается намеренно, и проверяется, что
тест падает.

| # | Случай | Ожидание |
|---|---|---|
| 1 | свежий lock, плагин не трогали | `ok:true`, все списки пусты |
| 2 | подменён байт в `_common.md` | `derived_stale` содержит **всех** агентов, у кого он в `sources`, и `changed_sources` называет именно его |
| 3 | подменён байт в одном шаблоне роли | `derived_stale` содержит **только** эту роль |
| 4 | правка собранного агента руками | `derived_tampered`, `sources` чистые, в `derived_stale` его нет |
| 5 | правка `skills/retro/SKILL.md` | только `normative_changed`; `derived` пуст |
| 6 | lock-файла нет, агенты есть | `ok:false`, `reason` = `no plugin-lock.json`, отличный от дрейфа |
| 7 | `seal` после случая 5 | `normative_changed` пуст, `derived` не изменился побайтово |
| 8 | `record` одной роли | записи остальных ролей и `normative` не изменились |
| 9 | агент удалён из проекта | `derived_missing`, не `stale` |
| 10 | новый файл под глоб `lib/*` | `normative_added` |

Плюс:
- `tests/lib/gate.test.sh` — `derived`-дрейф валит `gate.sh build`;
  дрейф только в нормативке — не валит, но кладёт `normative_changed` в
  `data`.
- `tests/lib/finalize.test.sh` — scope `sync` стейджит ровно два пути и
  ничего сверх.
- `tests/lib/skill-size.test.sh` — `sync` добавляется в цикл `GATE_MAX`
  (4096). Проверка фронтматтера получается бесплатно: цикл по
  `skills/*/SKILL.md` уже общий.

## 12. Миграция существующих проектов

Lock-файла нет ни у одного существующего проекта. Первый запуск `mvp:sync`
и есть миграция, и он обязан идти через Шаг 3 (Stop&Ask по стекам) — иначе
пришлось бы угадывать стек по фронтматтеру, что невозможно (§4.2).

Запрещено: печатать lock от текущего состояния проекта без пересборки. Это
залочило бы существующее расхождение как норму — ровно та ошибка, ради
которой механизм и делается.

`trellis` — первый живой прогон: lock отсутствует, агенты дрейфуют 5/5,
пять ролей (`backend-implementer`, `devops-engineer`, `frontend-implementer`,
`integration-specialist`, `test-writer`), стек `fastify` /
`docker-compose.fastify` / `react`. Заодно проверит Шаг 7 на реальном
материале: в нормативку попадут правки `_common.md` (раздел
`## Not executed`, принцип про exit-code и недоступность `grep -P` на BSD
grep) и шаблона devops (e2e-изоляция), причём по последнему в проекте уже
есть готовый код в `tests/e2e/helpers/compose.ts` — будет видно, совпадает
ли требование с тем, что проект сделал сам.

## 13. Отвергнутые варианты

**Перегенерировать `ci-mirror.sh` по маппингу стека.** Отвергнут: §3.
Не экономит работу, а уничтожает её.

**Декларативная карта влияния «файл плагина → проектные файлы».** Дала бы
адресный отчёт по нормативке вместо списка путей. Отвергнут: карта — третий
источник правды рядом с кодом и шаблонами, и она начнёт врать с первого
забытого обновления. В `derived` адресность достаётся бесплатно, потому что
связь «шаблон → агент» уже закодирована в `assemble-agent.sh`; в
`normative` её пришлось бы выдумывать.

**LLM-аудит проектных файлов на соответствие новым требованиям.** Сильнее
диффа, но это суждение: недетерминированно и ошибается в обе стороны.
Отвергнут в пользу «покажи дифф, решает оператор».

**Отслеживать только `templates/`.** Минимум шума, но половина нормативки
живёт в `SKILL.md` — например маппинг стек → `ci-mirror.sh` в
`mvp:bootstrap`. Отвергнут: пропустил бы ровно те изменения, ради которых
механизм делается.

**Только semver из `plugin.json`** и **только git sha** — §4.1.

**Миграции схемы `plan.json`/`state.json`** — §3, отложено до первого
настоящего разрыва.

## 14. Известные пределы

- Механизм не проверяет, что проектные файлы удовлетворяют новым
  требованиям. Он показывает, что требования изменились. Разрыв между этим
  и «проект соответствует» закрывается человеком или отдельной задачей
  плана.
- `normative`-дрейф можно игнорировать бесконечно: он не блокирует. Единственное,
  что его гасит — осознанный `seal`. Это компромисс в пользу работающего
  гейта (§7).
- `git_sha` в lock может указывать на коммит, которого нет в текущем
  чекауте плагина (переустановка, force-push). Шаг 6 в этом случае
  деградирует до списка путей без диффа — не ошибка.
- Проекты, собранные до `lock_version: 1`, неотличимы от проектов, где
  lock-файл удалили. Оба случая ведут в Шаг 3.
